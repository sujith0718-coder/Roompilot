## 1. Executive Summary & Problem Introduction (1 Minute)

> **"Judges, welcome to RoomWise.**
>
> In university campuses, scheduling is only half the battle. The true operational headache begins when classes must be mapped to physical spaces with varying capacities, smart boards, audio systems, and lab equipment. Worse, sudden disruptions—such as an AC leak, electrical fault, or maintenance closure—cause chaotic manual scrambling, double bookings, and severe timetable clashes.
>
> **RoomWise solves this with three core architectural pillars:**
> 1. **Automated Dual-Engine Allocation:** A fast First-Fit baseline paired with an Improved Heuristic optimizing capacity utilization and facility matching.
> 2. **Decoupled Independent Hard-Constraint Validation:** A strict, independent validator that verifies every assignment before committing to ensure zero capacity violations, zero missing facilities, and zero overlapping double-bookings.
> 3. **Dynamic Disruption Recovery Engine:** Minimal-churn reassignments when rooms close unexpectedly, with honest reporting of unresolved classes when constraints cannot be satisfied."

## 2. Architecture & Technology Stack (45 Seconds)

> **"Our architecture enforces strict separation of concerns:**
> * **Frontend:** React 18 with TypeScript, Vite, and Tailwind CSS.
> * **Backend:** Node.js, Express, and TypeScript running in ECMAScript Modules (`NodeNext`).
> * **Database & Persistence:** MongoDB with Mongoose ODM schemas for Users, Rooms, Bookings, and Audit Logs.
> * **Security & RBAC:** Central Express middleware verifying JWT tokens and enforcing role permissions across 8 distinct campus roles (`TUTOR`, `STUDENT_REP`, `EVENT_MANAGER`, `SECRETARY`, `HOD`, `COE`, `PRINCIPAL`, `SYSTEM_ADMIN`).
> * **Verification:** Vitest test suite running 52 unit and integration tests covering domain logic, API contracts, and security boundaries."

## 3. End-to-End Live Demonstration Sequence (3 Minutes)

Run the demonstration runner in the terminal:
```bash
npm run demo
```

### Stage 1: Load Synthetic Benchmark Dataset
* **What to Show:**
  * 6 physical classrooms with varied capacities (25 to 120 seats), diverse equipment (`PROJECTOR`, `AC`, `LAB_EQUIPMENT`, `SMART_BOARD`, `WHEELCHAIR_ACCESSIBLE`), and 1 intentionally blocked room (`BLOCKED-999` under pipe maintenance).
  * 6 representative booking requests spanning regular lectures, large convocations, specialized lab sessions, and seminars.
* **Talking Point:** *"All sample data is deterministic and isolated for development. It tests both ordinary and extreme constraint boundaries."*

### Stage 2: First-Fit Baseline Allocation
* **What to Show:**
  * First-Fit processes requests sequentially and assigns the first valid room found.
  * Correctly rejects `req-002` (200 students) because maximum room capacity is 120.
  * Execution time: ~2ms. Average capacity waste: 12 seats/room.
* **Talking Point:** *"First-Fit quickly satisfies requests, but as room inventory gets tight, early allocations can waste large halls on small classes."*

### Stage 3: Improved Heuristic Allocation
* **What to Show:**
  * Runs on the exact same requests and room inventory.
  * Prioritizes most-constrained requests first (fewer candidate rooms) and assigns the room that minimizes capacity waste (`room.capacity - request.enrollmentCount`).
  * Best-fit allocation matches the 95-student symposium to the 120-seat Auditorium, the 22-student seminar to the 25-seat Seminar room, and the 25-student lab to the Computing Lab.
* **Talking Point:** *"The improved heuristic evaluates request tightness first, preserving flexible rooms for classes that genuinely need them."*

### Stage 4: Independent Hard-Constraint Validation
* **What to Show:**
  * Both First-Fit and Heuristic outputs are piped through the decoupled `validateAssignmentStrict` engine.
  * Output: `✅ PASSED (0 hard constraint violations)`.
* **Talking Point:** *"Crucially, our system does not rely on the allocator's self-reported success. The validator independently verifies capacity, facilities, blockages, and timetable overlaps."*

### Stage 5: Comparative Analytics
* **What to Show:**
  * Direct empirical comparison generated by `metricsService.compareResults`.
  * Assigned count comparison, unresolved count, and average capacity waste.

### Stage 6: Disruption Event — Successful Minimal-Churn Recovery
* **What to Show:**
  * Simulated sudden event: Room `LH-101` is closed due to an emergency water leak.
  * Only 1 class was affected (`req-004`).
  * **Unaffected assignments preserved:** 4 classes remain in their rooms without unnecessary disruption.
  * **Reassigned class:** Moved smoothly to alternative available space `LH-102`.
* **Talking Point:** *"Notice the recovery engine minimizes churn. It does not re-shuffle the entire campus; it stabilizes existing allocations and moves only affected sessions."*

### Stage 7: Disruption Event — Honest Failed Recovery
* **What to Show:**
  * Simulated catastrophic failure: Computing Lab `LAB-201` undergoes total electrical circuit breaker failure.
  * Class `req-003` requires specialized `LAB_EQUIPMENT`.
  * **Recovery Output:** `Unresolved Bookings: 1 (req-003)`.
  * **Reason:** *"No alternative room available meeting constraints during recovery after room closure."*
* **Talking Point:** *"This is a key strength: rather than dangerously placing students in a lecture hall lacking lab hardware, RoomWise honestly flags the booking as unresolved for administrative escalation."*

## 5. Frequently Asked Questions (Judge Q&A)

### Q1: "Why not re-run full allocation from scratch when a room closes?"
> **Answer:** Full re-allocation causes massive schedule instability (churn). Moving 50 classes across campus creates confusion for faculty and students. RoomWise's recovery engine isolates affected bookings, preserves unaffected classes, and computes minimal reassignments.

### Q2: "How does the independent validator differ from the allocator?"
> **Answer:** The allocator uses heuristic scoring to search for an optimal room. The validator is an unyielding, decoupled gatekeeper that enforces hard boolean constraints: capacity, facilities, blockages, and schedule collisions. Even if an allocator produces an invalid proposal, the validator catches and blocks it.

### Q3: "What prevents a user from bypassing role restrictions through direct API calls?"
> **Answer:** Frontend role checks are purely for UI convenience. Express backend middleware (`server/src/middleware/auth.ts` and `server/src/middleware/rbac.ts`) verifies cryptographic JWT signatures and enforces role authorization on every single protected API route. Unauthorized direct API calls fail with `401 Unauthorized` or `403 Forbidden`.

### Q4: "What happens if MongoDB is offline during testing or demonstration?"
> **Answer:** Our seed and demo scripts feature safe offline fallbacks that export and load deterministic JSON datasets, ensuring reliable live presentations regardless of network or local database status.
